# Phase 5 feature 6: audit log

## What was built

- **No new logging was needed.** `daemon/audit.py`'s `record()` was
  already called unconditionally (success and failure alike) from
  `daemon/server.py`'s `dispatch()` for every single RPC op -- including
  every op every earlier Phase 5 feature just added -- so "every admin
  and customer action logged" was already true before this feature
  started; this is purely a read/search/export UI over the
  already-complete `AuditLog` table.
- `api/routers/auditlog.py`: reads `AuditLog` directly via
  `read_session()` (no RPC round trip) -- the same
  "forgehost-api opens the same SQLite file read-only for fast list/get
  queries" pattern ARCHITECTURE.md SS4 already establishes and
  `tokens.py` already uses, appropriate here since this is a pure read
  with zero privileged/system-mutating side effect.
  - `GET /api/v1/audit-log`: filters by `actor`/`op`/`target` (substring),
    `result` (exact `ok`/`failed`), and a general `q` search across
    actor/op/target/detail, paginated (capped at 500/page), newest first.
  - `GET /api/v1/audit-log/export.csv`: same filters, returns a real
    downloadable CSV (`Content-Disposition: attachment`).
  - **Deliberately no delete/mutate route anywhere in this file** (goal:
    "cannot delete via UI") -- verified structurally by a dedicated test
    asserting no route in either router object accepts
    DELETE/PUT/PATCH, not just by omission.
- `audit_log.html`: search/filter form, paginated table, CSV export link.

## Real bugs / decisions found by live testing

- None -- this feature is additive read-only surface over an
  already-correct, already-populated table; there was no state machine
  or system-mutation path to get wrong.

## Live verification

- `GET /api/v1/audit-log?page_size=5` against the real, live database
  (760 real rows at the time of this test, from every action taken
  across this entire Phase 5 build session) -> returned genuine recent
  rows in the correct newest-first order.
- `GET /api/v1/audit-log?op=firewall` -> the exact 8 real `firewall.*`
  rows generated by Feature 4's own live verification earlier this
  session, including the 3 real `firewall.add` `deny`-on-protected-port
  rejections with their exact error text in `detail`.
- `GET /api/v1/audit-log?result=failed` -> a real mix of rows across
  several different features (a rejected `services.status` call for
  `forgehost-api`, a rejected weak-password change, the firewall
  rejections above) -- confirmed the existing `_sanitize()` redaction
  from `daemon/audit.py` (Security audit era code, unmodified here)
  still correctly shows `"password": "***"` rather than a real value in
  a row surfaced through this brand-new UI.
- `GET /api/v1/audit-log/export.csv?op=firewall` -> real `200`, correct
  `Content-Disposition: attachment; filename=forgehost-audit-log.csv`
  and `Content-Type: text/csv`, and a real CSV body matching the
  filtered JSON view's rows exactly.
- Unauthenticated `GET /api/v1/audit-log` -> `401`.

## What's untested

- Behavior at genuinely large row counts (hundreds of thousands+) --
  `_query_rows` uses a real `SELECT COUNT(*)` (via
  `func.count().select_from(base.subquery())`) rather than materializing
  every matching row just to measure it, so pagination itself scales
  fine; not independently benchmarked against a synthetically huge table.
