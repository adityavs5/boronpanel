# Namespace Isolation Design for Forgehost LSAPI Workers

## Summary

Enable OpenLiteSpeed's own, already-compiled-in **Namespace Container** feature (`security{ namespace ... }` + a tokenized `namespaceConf` template, driven from inside `lscgid` — confirmed present in the exact `LiteSpeed/1.9.0 Open` build already running on this box, currently disabled) as the primary mechanism for giving every hosted account a private mount+user namespace: a private `/tmp`, a filtered `/etc` view, and a structural backstop against symlink-into-another-account's-docroot reads — on top of, not instead of, the existing DAC/POSIX-ACL/cgroups-v2 stack. This is preferred over building a bespoke `bwrap`-as-wrapper mechanism (a documented, viable fallback per the tool survey below) because OLS's own `ns_exec_ols()` runs **while `lscgid` is still root, before the suEXEC `setuid()` drop**, on every LSAPI parent (re)spawn — which sidesteps both the "no privileged moment after setuid" wall that blocked a cgroups-style helper before, and the need to invent a new permanently-supervised per-account anchor process that a self-built wrapper would require to persist its own namespace across worker recycles. Recommended namespace set: **mount + user** as the concrete initial deliverable (PID namespace is a likely-valuable follow-on, gated on confirming whether OLS's native feature already includes it — unconfirmed, see §8); **network and cgroup namespaces are explicitly excluded from scope**. This design closes a real, live-confirmed gap (cross-account `/tmp` enumeration via the project's own `open_basedir` string, which currently includes the shared system `/tmp`) and adds meaningful defense-in-depth, but it does **not** close the confirmed cross-account `/proc` `cmdline`/`status` leak unless the PID-namespace question resolves favorably, does not add network egress control, and — like every isolation layer this project has built — does not raise the ceiling against a shared-kernel exploit. Rollout should be strictly opt-in per account (a new uid-scoped enable/disable list, not a global flip), following the same validate-before-apply/rollback-on-failure discipline `daemon/configtx.py` already enforces for every other OLS config change, with canary accounts before any default-on behavior for new accounts, and a much later, separately-scoped decision about existing-account backfill.

## 1. Threat model

### What this design concretely prevents

| Attack / gap | Mechanism today | What namespace isolation adds |
|---|---|---|
| Cross-account `/tmp` file enumeration | None — `vhost.conf.j2`'s rendered `open_basedir` is `"<docroot>:<home>/tmp:/tmp"` (`vhost.conf.j2:59-83`), i.e. every account's PHP is explicitly sandboxed to include the **shared, world-writable, sticky** system `/tmp`. Content is uid-protected (mode `600`-ish), but filenames, existence, and timing of every other account's temp/session artifacts are visible today. | A private mount-namespaced `/tmp` (bind-mounted from that account's own `<home>/tmp`, already quota-accounted) makes the `:/tmp` clause resolve to an empty, private view per account — this is a project-specific, self-inflicted gap this design directly closes, not a generic "namespaces are good" claim. |
| Cross-account filesystem-view / fingerprinting | None — every process shares one mount namespace, one `/etc/passwd`, one view of `/home`. | Filtered `/etc` skeleton + a namespace-private view hides other accounts' usernames, home-directory existence, and installed-software/package-version fingerprinting from a compromised worker (CageFS's "skeleton" model). Soft benefit, not a hard boundary — the underlying files were never writable by the attacker either way. |
| Symlink-into-another-account's-docroot read (the `CVE-2026-54420` pattern: a LiteSpeed cPanel-plugin vuln where an account plants a symlink inside its own space pointing at another customer's files) | Kernel `fs.protected_symlinks=1`/`protected_hardlinks=1` (confirmed live) close the **classic** world-writable-sticky-dir race (the `CVE-2006-5178` class) but do **not** cover a symlink planted inside an account's own non-sticky, non-world-writable docroot pointing at a sibling account's docroot. **Confirmed, not merely suspected: `templates/vhost.conf.j2:2` hardcodes `allowSymbolLink 1` unconditionally for every vhost**, with no per-account or per-domain override — so OLS's own follow-symlink policy is already maximally permissive today, independent of this design entirely. This is a currently-live gap, not an open question (§8's prior framing of this as "unverified" was itself an oversight — the check is free, the file was already being read for the `open_basedir` line 58 lines below). | If a namespace only bind-mounts the account's own docroot/home into its private view (rather than relying purely on OLS's follow-symlink policy plus the shared-`nobody`-ACL model), a symlink to another account's path resolves to nothing inside that namespace — a structural backstop independent of whatever the vhost directive happens to be set to, and the most direct, already-justified reason this design is worth building regardless of how the PID-namespace question in §8 resolves. |
| PID/process enumeration and addressability (`cmdline`/`status` of every other account's and every system service's process, confirmed live-readable on this box today) | None — confirmed live: every OLS process (main, static workers, and by extension every LSAPI child, per this project's own Phase 2-6 empirical work) shares the host's PID namespace with PID 1. `environ`/`fd`/`maps` are already blocked cross-uid by `ptrace_may_access()` — this is **not** part of the leak. | A real PID namespace would make other accounts' processes **not exist** in a worker's PID space at all — stronger than a `hidepid=2` remount (which is also riskier to deploy on this specific systemd-heavy host; see the `ProtectProc=`/D-Bus caveats researched for Lane 4) because it removes addressability structurally rather than gating readability. **This benefit is contingent on confirming OLS's native feature actually creates a PID namespace — unconfirmed, §8.** If it turns out to be mount+user only, this specific leak is *not* closed by the recommended approach as-is. |

### What this design explicitly does not prevent — stated plainly, not smoothed over

- **`environ`/`fd`/`maps` cross-account reads.** Already blocked today by `ptrace_may_access()`, a plain DAC/capability check unrelated to namespaces. Namespace isolation is not solving a real problem here; don't credit it with closing a gap that doesn't exist.
- **Network-level attacks.** Every process on this box shares one network namespace (`net:[4026531840]`, confirmed live). A compromised PHP worker can already open arbitrary outbound TCP/UDP (spam relay, C2 beaconing, port scanning) regardless of Linux uid, and this design **deliberately excludes** a network namespace (see §2) — LSAPI's own IPC is a filesystem-pathname Unix socket, unaffected by net namespaces either way, and building real veth/bridge connectivity back out (needed for legitimate MariaDB/Postfix/outbound-HTTP use) is disproportionate machinery compared to the cheaper, namespace-free alternative (uid-scoped `nftables`/`iptables` egress rules), which remains a separate, independent piece of future work this design does not attempt.
- **Kernel-level exploits — the largest honest caveat.** Every namespace lives inside one shared kernel. `CVE-2016-5195` (Dirty COW), `CVE-2022-0847` (Dirty Pipe, independently demonstrated as a real container-escape primitive), and `CVE-2022-0492` (a `cgroup_release_agent` bug enabling cgroup/namespace-confinement escape) are all "one kernel bug defeats every tenant boundary simultaneously" precedents, and once an attacker has root via any of them, `setns()`/`nsenter` into any other account's namespace is trivial. This design raises the bar against a purely-DAC-and-uid-mediated attacker; it is **not** a backstop against a kernel bug, and should never be described to stakeholders as one.
- **CPU microarchitectural side channels.** Spectre/Meltdown-class attacks (and descendants such as 2025's VMScape work) exploit shared cache/branch-predictor state between processes on the same physical core — namespaces and cgroups don't touch this at all. A real fix needs core-pinning/`isolcpus`/SMT-disable per tenant, none of which Forgehost's cgroups-v2 CPU-quota mechanism does today (it limits *how much* CPU time, not *which core*), and this design does not add it.
- **Resource-based DoS beyond what cgroups already enforce.** Unaffected either way — CPU/mem/IO/pids limiting is already real, kernel-verified, and stress-tested (throttling, OOM-kill, `EAGAIN` on fork-cap) via the existing `forgehost-<username>.slice` mechanism (`daemon/cgroups.py`). Namespace isolation is orthogonal to this, not a replacement or an upgrade to it.
- **Concurrent-connection / entry-process limiting.** CloudLinux's LVE has a PAM-integrated concurrent-request limiter with no Forgehost equivalent today; this design does not add one.
- **Cron- or FTP-spawned processes.** This design, exactly like the existing cgroup reconciler (`_cgroup_reconcile_loop`, which only scans `system.slice/lshttpd.service`'s cgroup), is scoped to the LSAPI/`lscgid` spawn path. Cron jobs run via the real system crontab as the account's own uid, entirely outside this hook, and remain unisolated by it — an acknowledged, pre-existing gap this design inherits rather than closes.
- **The API-layer authorization boundary.** This is a separate, standing architectural risk (`ARCHITECTURE.md` §2, `AUDIT-THREATMODEL.md` §2): `forgehostd`'s RPC dispatch trusts that `forgehost-api` already checked ownership/RBAC and does not re-derive authorization itself. A namespace escape at the Linux-process level has nothing to do with, and cannot backstop, a missing `require_account_access()` check in the API layer — the two are unrelated failure classes, and this design does not touch that boundary at all.

## 2. Recommended approach

### 2.1 Namespace types

| Type | Verdict | Rationale |
|---|---|---|
| **Mount (`CLONE_NEWNS`)** | **In scope, primary deliverable** | Directly closes the `open_basedir:…:/tmp` self-inflicted gap (§1) and enables the `/etc` skeleton, at negligible cost, via a private-copy-plus-targeted-bind-mounts approach (the new namespace inherits the full existing mount table at creation — no `pivot_root`, no minimal rootfs needed, since shared libraries/PHP extension dirs/package-manager paths must keep resolving unchanged). |
| **User (`CLONE_NEWUSER`)** | **In scope, enabling prerequisite** | Not valuable for its own isolation properties here — it's the specific, kernel-sanctioned mechanism (confirmed enabled on this box: `kernel.unprivileged_userns_clone=1`) that lets a process construct further namespaces without `CAP_SYS_ADMIN` in the host namespace. For the OLS-native path (§2.2) this matters less directly since `lscgid` is root anyway; it matters if the design ever falls back to the custom-wrapper path, where the wrapper starts already privilege-dropped. |
| **PID (`CLONE_NEWPID`)** | **Conditional / phase-2, not the initial deliverable** | Cheap and delivers real value (closes the confirmed `/proc` `cmdline`/`status` leak, §1) but (a) it is **unconfirmed whether OLS's native Namespace Container feature creates one at all** (§8), and (b) `unshare(CLONE_NEWPID)` doesn't relocate the calling process — only children it forks land in the new namespace — so LSAPI's own "ProcessGroup" model (one persistent PHP parent that `fork()`s `PHP_LSAPI_CHILDREN` workers) would need a small dedicated init/reaper as the namespace's actual PID 1, not the LSAPI parent itself, to avoid a new failure mode: per `pid_namespaces(7)`, if a namespace's PID-1 process dies, the kernel `SIGKILL`s everything else in the namespace — today an LSAPI-parent crash safely orphans its children to the host's real init; naively making the LSAPI parent itself PID 1 of a new namespace would turn that same crash into "kill this account's entire warm worker pool instantly." Scoping this as a deliberate, later, separately-evaluated follow-on (not bundled into the first deliverable) avoids taking on that new failure class before the rest of the mechanism is proven. |
| **Network (`CLONE_NEWNET`)** | **Explicitly out of scope** | LSAPI's OLS↔worker transport is a filesystem-**pathname** Unix socket (`uds://tmp/lshttpd/<user>_php83.sock`, relative to `$SERVER_ROOT`) — network namespaces only scope the **abstract** UDS namespace and TCP/UDP ports, so a net namespace buys zero IPC benefit here. The real property it would add (egress containment) needs a veth pair with a privileged host-side attach step to keep MariaDB/Postfix/outbound-HTTP reachable — real plumbing, and strictly more moving parts than the cheaper, namespace-free alternative (uid-scoped firewall egress rules), which is a legitimate but separate future project, not part of this design. |
| **IPC (`CLONE_NEWIPC`)** | **Optional, bundle for free if convenient** | Essentially free to include alongside mount+user in the same `unshare()`/`ns_exec_ols()` call — no propagation gotchas, no PID-1/reaping semantics, auto-torn-down on last-process-exit. Low standalone value: hosted PHP/CMS software rarely uses System V IPC or POSIX message queues directly, and OPcache's typical `mmap`-based cross-worker sharing (the one plausible use case, given `PHP_LSAPI_CHILDREN=10`'s ProcessGroup mode) is inherited via plain `fork()`, bypassing SysV shm entirely. Include it if OLS's own template supports it trivially (it does, via the `mqueue` verb); don't build separate plumbing to force it. |
| **Cgroup (`CLONE_NEWCGROUP`)** | **Explicitly excluded** | The one namespace type with a *confirmed* interaction risk against a mechanism this project already depends on: cgroup v2's `nsdelegate` mount option (already active on this box) changes the authorization check for a `cgroup.procs` **write** to require both source and destination be reachable from the writer's own cgroup namespace. `forgehostd`'s `_cgroup_reconcile_loop` writes from the host's own root cgroup namespace today; nesting workers inside a per-account cgroup namespace is not needed to achieve any of this design's mount/PID/user goals and would only complicate that reconciler's correctness for no benefit. Not a "maybe later" — actively design around it. |

### 2.2 Tool/mechanism choice — three options, one clear winner

Three ways to actually implement mount+user (+optionally PID) namespace isolation for LSAPI workers were evaluated:

**(a) Hand-rolled `unshare()`/`clone()` wrapper, purpose-built for Forgehost.** Rejected outright: bubblewrap already exposes exactly the primitives a bespoke tool would reimplement (mount/pid/net/ipc/uts/user unshare, arbitrary bind mounts, exec), backed by far more real-world hardening (it's Flatpak's actual security boundary) than a new custom tool could match without a comparable, separate investment. No part of this research surfaced a reason to reinvent it.

**(b) `bubblewrap` (`bwrap`) substituted for the extProcessor's `path`.** A real, viable option and the best of the "wrapper-at-`path`" family: it's a purpose-built thin unprivileged exec-wrapper (not a container platform), it already has a first-party-precedented hook point in this exact codebase (the Phase 2-6 diagnostic-wrapper substitution at OLS's `path` field, done once already to observe post-setuid uid/cgroup state), and — critically, if invoked **without** `--unshare-pid` — it does a true single-process `execve()` substitution with zero added PID, preserving whatever PID-based bookkeeping OLS/`lscgid` do today (it is unconfirmed whether OLS enforces the extProcessor's `memSoftLimit`/`procSoftLimit`/etc. by inspecting the specific PID it spawned — treat `--unshare-pid` as an explicit, later, separately-justified tradeoff, not a default). Its structural weakness for this design: it runs strictly **after** `lscgid`'s `setuid()` drop (per §2.3), so it inherits the same "no privileged moment" constraint the cgroups design already hit — the only lawful way it can build a mount/PID namespace at all without a rejected setuid-root helper is `CLONE_NEWUSER`-rooted self-nesting, and because a user-namespace-owned mount/PID namespace is torn down by the kernel the instant its last referencing process exits, **persisting it across LSAPI-parent recycles requires inventing a new, permanently-supervised per-account anchor/keepalive process** — a genuinely new operational category this codebase has never had to build or run (cgroup slices, by contrast, persist as pure cgroupfs metadata with zero processes required inside them).

**(c) OLS's own native "Namespace Container" feature** (`security{ namespace 0|1|2 }`, a `namespaceConf`/`namespaceConfVhAdd` template file, `$UID`/`$GID`/`$USER`/`$HOMEDIR`/`$PASSWD`/`$GROUP` substitution tokens) — **recommended**. This is not a `path`-substitution hack at all; it is a first-class, already-compiled-in code path inside `lscgid.cpp`/`ns.c` (confirmed directly from OLS's own public source and independently corroborated by binaries already installed at `/usr/local/lsws/lsns/bin/` on this box), and its setup work (`ns_exec_ols()`) runs **before** `setuid()`, while `lscgid` still holds root — on **every** LSAPI parent (re)spawn, not just once. That last property is the decisive difference from option (b): because the privileged moment recurs naturally at every respawn (courtesy of `lscgid` always being root right before that fork), there is no need to invent a persisted, permanently-running anchor process at all — either the namespace state is reused via OLS's own optional `/var/lsns/<uid>/` persistence-plus-`setns()` optimization, or, absent that, `lscgid` simply re-runs the (cheap, single-digit-millisecond) `unshare`+bind-mount sequence fresh on the next spawn, exactly the way it does today for the cost-amortized-by-worker-pooling reasons LiteSpeed's own benchmarking already documents. Either way, **zero new supervised daemon is required**, in contrast to option (b).

### 2.3 Why this ties back to Lane 2's spawn-mechanics findings

The entire cgroups precedent (`daemon/cgroups.py`) exists because of one hard constraint, confirmed both by this project's own prior empirical work and independently re-derived from OLS's public source this round: **`lscgid` forks, drops privilege to the account's own uid/gid, and only then `execve()`s the extProcessor's `path`** — so anything substituted for `path` starts life already unprivileged, with no capability to migrate itself across a cgroup (or namespace) boundary it doesn't already own. That constraint is exactly what forced the cgroups design into "a periodic root-daemon reconciler does the privileged step out-of-band" rather than a setuid helper (rejected by this environment's own security review as a standing local-privesc surface on a mutually-untrusted box). The single most important finding from the OLS-source read is that **this same constraint does not apply to OLS's own native namespace feature**, because its privileged step (`ns_exec_ols()`) is placed *before* the `setuid()` call in the very same function that already does the privilege drop — it is, in effect, LiteSpeed's own already-shipped instance of exactly the "root does the privileged thing before the account gets control" pattern this project already committed to for cgroups, except no new daemon, no new reconcile loop, and no new binary is introduced into the account's execution path at all. Recommending option (c) over (b) is therefore not a stylistic preference — it is the direct, mechanical consequence of where in `lscgid`'s fork path each option's privileged work would have to happen.

## 3. LSAPI wrapper design

### 3.1 Primary mechanism — OLS-native interception (no separate wrapper process)

There is no bespoke "wrapper script" in the recommended design — the interception point is a **configuration directive inside OLS's existing config-generation pipeline**, not a new process inserted into the fork/exec chain. Concretely: `daemon/ols.py`'s `render_httpd_config()` gains one new, small, server-level `security{}` block (`namespace 1`, pointing at a `namespaceConf` template path), and the per-uid on/off gate is controlled separately via OLS's own `lsnsctl enable-uid <uid>` / `disable-uid <uid>` (a runtime state toggle, distinct from the full `httpd_config.conf` regeneration cycle — see §5 for why that distinction matters for rollback speed). No change is needed to the per-account `extProcessor` block (generated by `_all_active_vhosts()`, `ols.py:213-259`, rendered at `templates/httpd_config.conf.j2:238-260`) or to the per-domain `scripthandler` reference (`templates/vhost.conf.j2:16-18`) — the account's existing `path`/`extUser`/`extGroup` stays exactly as rendered today.

```
Request arrives at OLS shared "nobody" worker
        |
        v
vhost resolved -> scripthandler -> lsapi:<user>_php83   (unchanged, today's config)
        |
        v
lscgid forks   (still root, uid 0, gid 65534 — confirmed live on this box)
        |
        v
IF security.namespace is enabled AND this account's uid is not in the
   lsns disabled-uid list (our new per-account opt-in gate):
        |
        v
  ns_exec_ols():
    check /var/lsns/<account-uid>/ for a persisted namespace
      EXISTS      -> setns() into it (mount[, user[, ipc]])   [fast path]
      NOT EXISTS  -> unshare(CLONE_NEWNS | CLONE_NEWUSER [| CLONE_NEWIPC])
                     mount(MS_PRIVATE | MS_REC, "/")   <- re-mark private;
                        this systemd host makes "/" rshared by default,
                        so skipping this step would leak the account's
                        bind mounts straight back to the host and to
                        every other account's namespace
                     apply namespaceConf template (see Section 4)
                     persist under /var/lsns/<account-uid>/  [optional,
                        perf optimization only — see open question in §8]
        |
        v
apply_rlimits_uid_chroot_stderr():  setuid(account uid) / setgid(account gid)
        |                            <- suEXEC drop happens AFTER namespace
        v                               setup, per lscgid.cpp's confirmed order
execve(lsphp83/bin/lsphp)
        |
        v
Account's LSAPI parent process now running: namespaced (private /tmp,
filtered /etc view) AND unprivileged (account's real uid/gid) simultaneously
        |
        v
LSAPI parent fork()s PHP_LSAPI_CHILDREN worker children as load requires
  -> every child inherits namespace membership automatically at zero
     extra cost (fork() propagates namespace membership for free)
  -> children self-exit at LSAPI_MAX_REQS (default 1000) / LSAPI_MAX_IDLE
     (default 60s); parent exits at LSAPI_PGRP_MAX_IDLE or crash
  -> next spawn re-enters this same lscgid fork path from the top
```

Because the namespace-setup step is inside `lscgid`'s own already-root fork path, no new process, no new systemd unit, and no new "is it still alive" monitoring surface is introduced by the primary mechanism. The account's existing uid, cgroup slice (`forgehost-<username>.slice`), and `extUser`/`extGroup` pin are all unaffected — this is additive to the existing suEXEC model, not a replacement for it.

### 3.2 Fallback mechanism — bubblewrap-as-wrapper (only if the native feature proves unusable)

Retained here as the documented, evaluated fallback in case §8's open questions resolve unfavorably (e.g. the vhost-vs-account granularity mismatch turns out to be a hard blocker for the native feature in Forgehost's one-extProcessor-per-account topology):

```
lscgid forks, ALREADY setuid-dropped to the account's own uid/gid,
THEN execve()s the extProcessor's `path`
        |
        v
path = a per-account wrapper invoking bwrap directly, e.g. conceptually:
   bwrap --unshare-user --unshare-ns --unshare-ipc \
         (deliberately NOT --unshare-pid, to preserve single-PID
          transparency for whatever OLS's own memSoftLimit/procSoftLimit
          enforcement keys off — see the open follow-up in Section 2.2)
         --bind <home>/tmp /tmp \
         --ro-bind <etc-skeleton-entries> ... \
         --bind /usr/local/lsws/tmp/lshttpd /usr/local/lsws/tmp/lshttpd \
            (defensive: keep the LSAPI socket directory explicitly
             reachable in case any future skeleton-hiding pass ever
             broadens beyond "just /tmp and /etc")
         -- /usr/local/lsws/lsphp83/bin/lsphp
   [illustrative sketch of the invocation shape only, not literal
    deployable config — the actual argv would be assembled by
    daemon/ols.py's template rendering, analogous to how extProcessor
    blocks are rendered today]
        |
        v
bwrap (already unprivileged, uid = account's real uid):
   unshare(CLONE_NEWUSER) -> write uid_map/gid_map (self -> self, or
      self -> 0 "root" purely inside the new namespace's own frame of
      reference — this does NOT change what uid the host, other
      accounts, or forgehostd's cgroup reconciler observe; every real
      DAC/quota/cgroup check keys off the unmapped host uid regardless)
        |
        v
   now holds CAP_SYS_ADMIN, but ONLY inside this new user namespace
        |
        v
   unshare(CLONE_NEWNS[, CLONE_NEWIPC])
   mount(MS_PRIVATE | MS_REC, "/")
   apply the same bind-mount layout as Section 4
        |
        v
   execve(real lsphp binary)   <- no new PID created by this exec;
      single-process transparency to lscgid/lshttpd is preserved
      because execve() never changes a process's PID
        |
        v
PERSISTENCE GAP (the real added cost of this fallback vs. the primary
mechanism): when this LSAPI parent exits/recycles, its CLONE_NEWUSER-
rooted namespace is reclaimed by the kernel unless something keeps it
referenced. setns(2) back into a namespace requires CAP_SYS_ADMIN in
the caller's own user namespace AND in the namespace that OWNS the
target namespace — a namespace this same account's uid created can be
rejoined by a later same-uid process, but ONLY if something has kept it
alive in the meantime. That "something" does not exist yet anywhere in
this codebase and would need to be designed, built, and operated as a
new per-account supervised anchor/keepalive process — a materially
larger, more novel piece of work than anything the primary mechanism
(Section 3.1) requires.
```

The fallback is included for completeness and because it was the best answer available before the OLS-native feature was discovered — it should not be started unless §8's granularity/PID-coverage questions specifically rule out the primary mechanism.

## 4. Bind mount layout

Because the recommended mechanism inherits the full existing mount table at namespace creation (no `pivot_root`, no minimal rootfs — per the mechanics research, this is deliberately the lighter of the two available approaches and matches Forgehost's actual need), the layout below is a set of **targeted overrides layered on top of an otherwise-unchanged view**, not a from-scratch container filesystem.

| Host path | Namespace view | Verb (OLS `namespaceConf` DSL) | Notes |
|---|---|---|---|
| `<home>/tmp` (already exists, already ext4-quota-accounted, already referenced in `open_basedir`) | `/tmp` | `bind` (read-write, not `tmpfs`) | Using the account's *existing* `<home>/tmp` directory rather than a fresh `tmpfs` keeps this counted against the account's current disk quota and costs nothing new to provision. Switching to a fresh per-account `tmpfs` instead would silently move PHP session/tmp data off ext4-quota accounting and onto the cgroup `MemoryMax` budget — a real semantics change that should be a deliberate future decision, not a side effect of this design. |
| `<home>/public_html`, other per-domain docroots under `<home>` | same path, unchanged | *(no explicit verb needed)* | Inherited automatically from the copied mount table — this is the reason `open_basedir` strings, the existing POSIX-ACL grant to `nobody` (`_grant_webserver_acl`/`ensure_docroot()`, `daemon/handlers_domain.py:160-216`), and every existing vhost/docroot path stay byte-for-byte identical. This design changes nothing about how the shared static-serving `nobody` worker resolves paths — it only changes what the account's own **LSAPI/PHP process** sees. |
| Curated `/etc` entries: `passwd`, `group`, `hosts`, `resolv.conf`, `nsswitch.conf`, timezone data, CA bundle, and any hosting-stack-specific paths (mirroring the default template's already-observed `/opt/cpanel`-style `bind-try` entries) | filtered/synthesized per-account view | `ro-bind` / `ro-bind-try` for files that must exist verbatim (`hosts`, `resolv.conf`, CA bundle); a **generated, filtered** `passwd`/`group` (via `copy`/`copy-try` of a pre-rendered file, substituted with `$UID`/`$USER`/`$PASSWD`/`$GROUP` tokens) rather than a straight bind of the real system file | The filtered `passwd`/`group` must remain resolvable for whatever `getpwnam()`/`getgrnam()`-style lookups PHP or hosted CMS software legitimately performs (the account's own entry, plus functionally necessary system accounts like `nobody`, `mysql`, `vmail`) — over-aggressive filtering risks breaking already-live-tested app behavior (WordPress/Joomla/PrestaShop) in a way that would only surface via live testing, not code review; see open question in §8. |
| `/usr/local/lsws/tmp/lshttpd/` (the actual directory backing `uds://tmp/lshttpd/<user>_php83.sock` — note this is **under `$SERVER_ROOT`, not the system-wide `/tmp`**) | unchanged, same path | *(inherited automatically — this path is never masked by the `/tmp` override above, since it is a different directory entirely)* | This is the one concrete detail that could silently break LSAPI's own OLS↔worker handshake if gotten wrong. Because only the system `/tmp` is being replaced (not `/usr/local/lsws`), the socket directory is unaffected by construction under this design's scope — but this should be called out explicitly and verified live (a namespaced worker successfully binding/connecting through this exact path) before any rollout, precisely because it is easy to conflate "isolate `/tmp`" with "isolate everything under a path literally named tmp." If a future pass broadens the `/etc`/filesystem-hiding scope toward a fuller CageFS-style skeleton, this path must be added as an explicit `bind`/`bind-try` entry rather than relying on inheritance. |
| `/usr`, `/usr/local/lsws/lsphp8x/`, shared `.so` libraries, `ld.so.cache` | unchanged, same path, read-only in practice (never account-writable today) | *(inherited automatically; no verb needed)* | Namespace isolation adds no write protection here that DAC doesn't already provide (these paths are already root-owned, world-readable-only) — its only contribution is optionally **hiding** exact installed package versions/paths from a compromised worker (a recon-reduction benefit), which is out of scope for the initial deliverable and can be layered on later without touching this design's core mechanism. |
| `/var/vmail/`, other accounts' `/home/<other-user>/` | not separately masked in the initial deliverable | *(rely on existing DAC: home dirs are already `711`, docroots `750`, non-account-owned)* | The mount table is a *copy*, so these paths remain technically present in the namespace unless explicitly hidden — DAC already prevents traversal/read today (confirmed via prior live cross-account `cat` attempts), so this is not a new gap, but a fuller CageFS-style "you literally cannot see other users exist" hiding pass (masking `/home` itself to show only the account's own directory) is a natural, separate follow-on once the core mechanism above is proven, not part of the initial scope. |
| `/proc`, `/dev` | unchanged unless a PID namespace is also adopted (§2.1, conditional) | `proc`, `dev` verbs are available in OLS's DSL for this purpose | A private `/proc` mount only meaningfully hides other processes' entries if paired with an actual PID namespace — a bind-style `/proc` override without one still reflects the host's real process table, so this row is explicitly gated on resolving the PID-namespace open question in §8 before it does anything useful. |

**Mount-propagation correctness detail, stated once because it is the single easiest thing to get wrong**: since Ubuntu 24.04/systemd marks the root filesystem `rshared` by default (specifically so container tooling gets host mounts "for free"), any `unshare(CLONE_NEWNS)` must be immediately followed by `mount(MS_PRIVATE | MS_REC, "/")` (or the DSL/tool's equivalent) **before** any bind-mount is performed inside the new namespace — otherwise every bind-mount (the private `/tmp`, the filtered `/etc`) propagates straight back out to the live host and to every other account's already-active namespace, silently defeating the entire mechanism while looking, from the outside, like it's working. This applies identically whether the primary (OLS-native) or fallback (`bwrap`) mechanism is used, and should be an explicit, named test in whatever validation step gates rollout (§6).

## 5. Provisioning changes

This design deliberately reuses every extension point the project already has rather than inventing new lifecycle shapes.

**Config-writer discipline.** Any change to `httpd_config.conf` needed to turn the `security{ namespace 1 }` block and `namespaceConf` path on at the server level must go through the same `ConfigWriterMulti` contract every other OLS config change already uses (`daemon/configtx.py`): render the candidate config to a `.tmp.<pid>` sibling → `validate()` → `backup()` the live file → atomic `os.replace()` → `reload()` (which, per OLS's own documented quirk, is where the *real* `openlitespeed -t` check actually happens, since `-t -c <path>` silently ignores a candidate-path override) → `verify()` → automatic rollback-and-restore-from-backup on any reload/verify failure. No new engine is needed — the same one OLS/Postfix/Dovecot writers already share is a subsystem-agnostic `targets: dict[name, path]` contract designed exactly for this kind of addition.

One deliberate gap in that existing contract needs to be called out and closed for this specific feature: `ols._verify()` today is `systemctl is-active lshttpd` — coarse enough to miss "lshttpd is running fine, but this one specific account's namespace setup is silently broken and its PHP now 500s." A misconfigured `namespaceConf` template (a bad bind-mount path, a missing `ro-bind-try` fallback) would not crash `lshttpd`, so the existing `verify()` would report success and never trigger rollback. **Recommend augmenting `verify()` for this specific config change with a synthetic canary-account HTTP probe** — hit a known health-check PHP endpoint under a designated canary account immediately after reload, confirm a `200`, and only then consider the change verified — rather than relying solely on the existing service-level check for a change whose failure mode is per-account, not server-wide.

**Per-account gating: a new uid-scoped list, not a global flip or a min-uid floor.** OLS's own `lsnsctl enable-uid <uid>` / `disable-uid <uid>` operates per-uid — this maps naturally onto Forgehost's one-Linux-user-per-account invariant and sidesteps the vhost-vs-account granularity question entirely for the on/off decision (the *content* of the namespace template stays one shared, mostly-static file using `$UID`/`$HOMEDIR`/etc. substitution tokens — no per-account file needs to be rendered the way per-account `extProcessor` blocks are today). This uid-list toggle is a separate, lighter-weight state change than the full `httpd_config.conf` regenerate-and-reload cycle above — worth confirming live (§8), since if true it means an emergency per-account disable during a bad rollout is materially cheaper and faster than the full validate/apply/rollback cycle needed for a global directive change.

**New hooks, following the existing hook-list pattern (`CREATE_HOOKS`/`TERMINATE_HOOKS`/`SUSPEND_HOOKS`/`UNSUSPEND_HOOKS`, registered in `daemon/server.py`, consumed in `daemon/handlers_account.py`):**

- **Create / first `domain.add`**: matching the existing convention that `account.create` itself touches no OLS state (vhost/PHP provisioning is deferred to `handlers_domain.add_domain` → `ols.provision_vhost()`), a new hook — call it `namespaces.enable_for_account(account)`, registered alongside `cgroups.apply_limits` — calls the uid-enable step at the same deferred point, not at raw account creation. No per-account file rendering is needed (per the shared-template point above), which keeps this hook lightweight relative to `ensure_docroot()`'s work.
- **Suspend / unsuspend**: **no change needed.** Precisely mirroring how suspend today does *not* recycle an already-warm LSAPI worker (it only rewrites the vhost to serve the static suspended page plus `usermod -L`), a namespaced worker is allowed to keep running through a suspend cycle — consistent with "unsuspend is a pure metadata flip." If immediate teardown on suspend is ever wanted for policy reasons, reuse the existing narrow primitive `sysops.recycle_php_workers(username)` rather than inventing a new one, and treat inclusion of the namespace/anchor state in that recycling as an explicit, separate decision.
- **Terminate**: `sysops.delete_linux_user()`'s existing `pkill -9 -u <username>` (already run before `userdel`, specifically because long-lived LSAPI workers otherwise survive as orphans under a freed uid) already reaps every namespaced process for that account with **zero new code**, since `pkill -u` matches by real host uid regardless of what mount/PID/user namespace a process privately belongs to. What is **not** already covered is the namespace's own backing filesystem state — any persisted `/var/lsns/<uid>/` entry needs an explicit new `TERMINATE_HOOKS` entry (`namespaces.teardown_account(account)`, calling the equivalent of `lsnsctl unmount --uid <uid>` and `disable-uid <uid>`), placed adjacent to `cgroups.remove_slice` in the existing, exact registration order (`ols.terminate_vhost` → DNS → databases → mail → SSL → cron → `cgroups.remove_slice` → FTP → php_ini → …). This is directly motivated by an already-observed, closely analogous leak: two **terminated** test accounts' `forgehost-cust1.slice`/`forgehost-demo2.slice` cgroup slices were found still lingering live on this box, suggesting `remove_slice` doesn't always fire/succeed cleanly on every historical termination. The same failure class (a hook not firing, or firing but failing partway) is foreseeable here too, and should be designed against from day one — including a periodic reconcile sweep (mirroring `bootstrap_all_slices()`'s reboot-recovery role for cgroups) that finds `/var/lsns/<uid>` entries for uids with no corresponding active `Account` row and cleans them up, rather than relying solely on the termination hook firing correctly every time.
- **Reactivate**: must not repeat the exact failure class this project has already been burned by four separate times in one feature (`docs/CHECKPOINT-phase2-7.md`'s backup/restore bugs) — a reactivate path that finds a surviving `Account` row must actively re-run `namespaces.enable_for_account()`, not silently assume the namespace/skeleton state survived alongside the DB row just because the Linux user did.

**Schema.** If any new persistent per-account state is needed beyond OLS's own `/var/lsns/<uid>/` filesystem state (e.g., an explicit opt-in flag for the phased rollout in §7), follow this project's own established convention and add a **new table** (e.g. `AccountNamespaceState(account_id, enabled, enabled_at)`) rather than a new column on `Account` — `Base.metadata.create_all()` only creates new tables, never `ALTER`s existing ones, and this exact gap has already bitten the project three times (cgroups' own `cpu_pct`/`mem_mb` columns, SpamAssassin's Phase 4-1 columns), while `DkimKey`/`PhpIniOverride` deliberately dodged it by choosing new tables. A new column here would need a manual, undocumented-by-the-ORM `ALTER TABLE` against the live install — avoidable entirely by following the table-not-column precedent.

## 6. Risks + mitigations

| Risk | Detection | Mitigation / rollback |
|---|---|---|
| **Mount-propagation leak** (forgetting `MS_PRIVATE|MS_REC` before bind-mounting, given this systemd host's default `rshared` root) silently defeats isolation while looking like it's working | A specific, named validation test before any rollout: write a marker file inside one canary account's private `/tmp`, confirm it is **absent** from the real host `/tmp` and from a second test account's private `/tmp` view | Nothing to "roll back" per se — this is a correctness bug in the template/mechanism itself, caught by the test above before it ever reaches a real account; if discovered post-rollout, immediately `disable-uid` every enabled account (fast path, §5) while the template is fixed |
| **Vhost-vs-account granularity mismatch**: OLS's `namespace`/`namespaceConf` directives are documented at server/vhost level, and Forgehost has one shared `extProcessor` per account referenced by potentially many per-domain vhosts — genuinely unclear whether per-vhost enablement (as opposed to the recommended per-uid `lsnsctl` gate) would produce one namespace, duplicate namespaces, or a conflict | Live test with a real two-domain account: provision domains A and B under one account, compare `/proc/<lsphp-pid>/ns/mnt` inode across a request to each — same inode = confirmed account-scoped as expected | Recommended design already routes around this by controlling activation via the per-uid `lsnsctl enable-uid` gate rather than a per-vhost directive — if server-level `namespace 1` still requires *some* per-vhost acknowledgment to take effect (unconfirmed), that acknowledgment should be rendered identically into every one of an account's vhosts by the existing template loop, never selectively |
| **`/etc/passwd` over-filtering** breaks a `getpwnam()`/`getgrnam()` call some hosted CMS or PHP extension legitimately makes (e.g. mail-related UID lookups) | Regression run against this project's own already-live-tested app stack (WordPress, Joomla, PrestaShop) after enabling on a canary account, watching for any new PHP warnings/errors tied to user/group resolution | Keep the filtered skeleton **inclusive** of functionally-necessary system entries (the account's own user, `nobody`, `mysql`, `vmail`, any mail-sending identity) rather than aggressively minimal; `disable-uid` the affected account immediately if a regression surfaces |
| **PHP `mail()`/`sendmail` breakage** if the namespace hides the binary or socket the local MTA path needs | Send-mail smoke test (WordPress/Joomla's own contact-form or password-reset mail flow) on the canary account | OLS ships a first-party escape hatch for exactly this (`hostexec.conf`, a list of binaries — `sendmail`, `passwd` in OLS's own examples — that run **outside** the namespace) — use it rather than punching ad hoc holes in the skeleton; exact syntax and interaction with Forgehost's Postfix-based stack is an open question requiring live testing (§8) |
| **LSAPI socket handshake breaks** if a future skeleton-hiding pass masks more of the filesystem than "just `/tmp` and `/etc`" and inadvertently shadows `/usr/local/lsws/tmp/lshttpd/` | Immediate, total failure mode (every request to the affected account 502s) — would be caught instantly by the augmented canary-probe `verify()` step (§5), not silently | Explicit `bind`/`bind-try` entry for that exact path in the template, called out permanently in this doc (§4) as a "do not forget" item for any future scope expansion |
| **Full-server blast radius of a config mistake** — `httpd_config.conf` is fully regenerated on every change (never incrementally patched), so a mistake in the new `security{}` block risks affecting every vhost simultaneously, not just namespace-enabled accounts | `ConfigWriterMulti`'s existing validate-before-apply step (§5) catches syntactically-invalid config before it ever reaches the live file; the augmented per-canary-account HTTP-probe `verify()` step catches a syntactically-valid-but-functionally-broken config that the existing coarse `systemctl is-active` check would miss | Automatic rollback-and-restore-from-backup, already built into `ConfigWriterMulti`, fires on either failure; because per-account enablement is gated by the separate, lighter `lsnsctl` uid list (not by editing `httpd_config.conf` per account), a single account's bad namespace behavior should never require a full server-config rollback in the first place — reserve the full rollback path for a genuinely broken shared template, and the per-uid `disable-uid` toggle for a single account's regression |
| **Stale `/var/lsns/<uid>` state surviving termination**, the same leak class already observed for cgroup slices (`forgehost-cust1.slice`/`forgehost-demo2.slice` found still present for terminated accounts) | Periodic sweep (mirroring `bootstrap_all_slices()`) comparing `/var/lsns/*` entries against active `Account` rows | New `TERMINATE_HOOKS` entry (§5) plus the periodic sweep as a backstop, built from day one given this exact failure class already has one confirmed precedent in this project |
| **Backup/restore or any non-standard write path recreates an account's files without re-establishing namespace/bind-mount state** — directly analogous to the already-found "`tar` restore doesn't preserve POSIX ACLs" bug (`CHECKPOINT-phase2-7.md`), which required an explicit re-call to `ensure_docroot()` after restore | Live end-to-end restore test on a namespace-enabled canary account, checking whether post-restore requests still resolve correctly | Any new backup/restore/snapshot feature that touches an account's docroot or `<home>/tmp` needs to explicitly re-invoke the namespace provisioning step, exactly as `ensure_docroot()` already needs re-invoking post-restore for ACLs — document this requirement alongside the existing ACL one, since it is the same underlying lesson recurring in a new place |
| **Kernel-exploit ceiling** — namespace isolation adds no protection against a shared-kernel privilege-escalation bug | N/A — not detectable or mitigable at this layer | None available at this layer; document honestly (§1) rather than represent this design as closing that risk |
| **Latency regression if namespace entry happens per-request rather than per-LSAPI-parent-spawn** | Timing comparison of request latency before/after enabling, specifically isolating cold-parent-spawn requests from warm-pool requests | If observed, this would indicate the mechanism is not amortizing the way the pooled-worker model assumes and should block rollout until understood — expected behavior, based on LSAPI's own `PHP_LSAPI_CHILDREN`/pooling model, is that the cost is paid once per parent lifetime (which can span thousands of requests), not per request |

## 7. Implementation order

1. **Phase 0 — Answer the blocking open questions on this real box first** (§8, especially: vhost-vs-account granularity, whether the native feature includes a PID namespace, `/var/lsns` persistence mechanics, and whether OLS's `memSoftLimit`/`procSoftLimit` enforcement is PID-keyed). This must happen *before* any provisioning code is written — several of these findings directly determine whether §2's recommended mechanism is even viable as scoped, or whether the fallback (§3.2) becomes necessary.
2. **Phase 1 — Manual, unwired validation.** Author the shared `namespaceConf` template and `/etc` skeleton set as static files (analogous to how `httpd_config.conf.j2` itself is authored and reviewed today). Enable via `lsnsctl enable-uid` on a single disposable test account, entirely by hand, with **no** `forgehostd` code changes yet. Confirm: private-`/tmp` isolation (the marker-file test from §6), docroot/`open_basedir` behavior unchanged, LSAPI socket handshake intact, mail-sending smoke test via `hostexec.conf`, and a regression pass against the already-live-tested app stack (WordPress, Joomla, PrestaShop).
3. **Phase 2 — Wire in as strictly opt-in, not yet in any default hook path.** Add the `AccountNamespaceState` table (or equivalent), a new admin-only RPC op/API endpoint that a human operator calls per account, routed through the `ConfigWriterMulti`-wrapped provisioning path from §5. Existing account creation, and every other account, remains completely untouched at this phase.
4. **Phase 3 — Canary.** Enable for one or two real, low-risk accounts (a dedicated canary account, or the box's existing single active test account) for a soak period. Monitor via the augmented canary-probe `verify()` step (§5) plus manual spot checks in this project's own established style (live `posix_geteuid()`/namespace-inode-comparison checks, not just mocked assertions), and explicitly re-confirm that `usage.py`'s `ps -u`/`du` metrics and the cgroup reconciler's uid-based PID matching are unaffected — expected to be fine per the research, but this project's own history (the FTP-chroot gap that sat undetected for two full phases) is a direct argument for verifying empirically rather than trusting the analysis.
5. **Phase 4 — Default-on for new accounts only.** Wire `namespaces.enable_for_account()` into the existing `CREATE_HOOKS`/`domain.add` hook list (§5), following the account-create-defers-to-domain-add convention already established. Existing accounts remain untouched and opt-in at this point — this is a deliberate, later, separately-scoped decision, not a side effect of turning it on for new accounts.
6. **Phase 5 — Staged backfill to existing accounts**, batched (e.g. lowest-traffic accounts first, or during announced maintenance windows), each batch soaked and confirmed healthy before the next, with the per-uid `disable-uid` toggle as the fast emergency rollback for any single regressed account.
7. **Phase 6 (stretch, explicitly separate) — PID namespace.** Only pursued once Phase 5 is stable and only after §8's PID-namespace-coverage question is resolved one way or the other: either confirm OLS's native mechanism already includes it (best case, no new work), or design and build the dedicated init/reaper shim discussed in §2.1 as its own separately-reviewed piece of work — not bundled into the initial mount+user rollout above.

## 8. Open questions

These are the specific items every research lane flagged as genuinely unresolved from docs/source alone, requiring live, read-only testing on this real box (or an equivalent disposable test account) before implementation can proceed with confidence. Listed roughly in priority order for Phase 0.

1. **Vhost-vs-account granularity for OLS's `namespace`/`namespaceConf` directives.** Does enabling at the vhost level, for an account with multiple domains sharing one `extProcessor`, produce one namespace per account (matching Forgehost's existing invariant) or something else? Needs a live two-domain test account with `/proc/<pid>/ns/mnt` inode comparison across requests to each domain. Highest priority — this could change the recommended provisioning mechanism in §5.
2. **Does OLS's native `ns_exec_ols()` actually create a PID namespace by default**, or only mount(+user[+ipc])? This single fact determines whether the recommended approach, as scoped for the initial deliverable, closes the confirmed live `/proc` `cmdline`/`status` cross-account leak (§1) or only the `/tmp`/`/etc` gaps. Needs either a deeper read of `ns.c`/`nsopts.c` than this research pass covered, or live inspection of a namespaced `lsphp` process's `/proc/<pid>/ns/pid` inode against the host's.
3. **Is the LSAPI listening socket fd pre-bound-and-inherited, or bound by the LSAPI library after `exec()`?** Affects whether any additional bind-mount beyond the one already called out in §4 is needed for the socket handoff to survive namespace setup. No `lsphp` process is currently running on this box (zero provisioned domains), so this needs a live domain provisioned and `ss -xp`/`/proc/<pid>/fd` inspection (read-only).
4. **Actual runtime mechanics of `/var/lsns/<uid>/` persistence and `lsnsctl unmount` cleanup.** Neither `/var/lsns` nor `lsns.conf` currently exist on this box (the feature has never been turned on here) — none of the persist/`setns`-join/unmount lifecycle inferred from binary `strings` output has been observed running for real. This directly determines whether persistence needs a live-process reference (in which case it may reintroduce some version of the anchor-process cost from §3.2) or is a zero-process bind-mounted-nsfs-reference trick (in which case it doesn't). Needs a genuine enable/test/unmount cycle on a disposable account.
5. **Does OLS enforce the extProcessor's `memSoftLimit`/`memHardLimit`/`procSoftLimit`/`procHardLimit` by inspecting the specific PID it spawned?** If so, any future PID-namespace addition (native, or via the `bwrap --unshare-pid` fallback) that inserts a distinct PID-1 wrapper process would silently defeat that OLS-native control — this needs to be confirmed (or ruled out) before Phase 6 (§7) is scoped, not discovered after the fact.
6. **Exact semantics of the raw `namespace 0/1/2` (and `cgroups 0/1/2`) integer levels** in the non-XML config format `httpd_config.conf.j2` uses — `lssetup`'s own source manipulates these as plain integers with threshold comparisons but never states in prose what each level means beyond "disabled" at 0. Needs either a deeper OLS source read or direct empirical testing (set each value, observe behavior).
7. ~~Whether a permissive OLS "Follow Symbolic Link" vhost directive currently allows the `CVE-2026-54420`-style cross-docroot symlink read today~~ — **resolved during review, not actually open**: `templates/vhost.conf.j2:2` hardcodes `allowSymbolLink 1` unconditionally, confirming this is a currently-live gap independent of namespaces (see the updated Threat Model row in §1). Left here, struck through, as a reminder that this list should have been double-checked against already-cited files before publishing rather than after — the same file was already being read elsewhere in this document for its `open_basedir` line.
8. **`hostexec.conf` syntax and its interaction with Forgehost's Postfix-based mail stack and `usermod`/`chpasswd`-driven account lifecycle.** Mentioned in OLS's docs only in passing, with no example syntax retrieved during this research pass — needed before the mail-sending mitigation in §6 can be implemented, not just referenced.
9. **What exact `getpwnam()`/`getgrnam()`-relevant system entries** (the account's own user, plus `nobody`, `mysql`, `vmail`, any others) must remain resolvable inside a filtered `/etc/passwd`/`group` skeleton without breaking already-live-tested CMS/PHP behavior — not yet worked out for Forgehost's specific stack (CloudLinux's CageFS is known to get this right for its own use case, but that doesn't transfer directly).
10. **Whether any hosted PHP version's default `session.save_path` is overridden per-account today.** If not, shared-session-file enumeration across accounts is a live gap structurally identical to the `/tmp`-enumeration gap this design already addresses (§1) — worth confirming whether the private-`/tmp` bind mount incidentally also fixes this (likely, if session files land under `/tmp` by default) or whether it needs separate handling.
11. **Whether the "no privileged moment to `setns()` back into a namespace" problem is genuinely fully sidestepped by OLS's own privileged-recreation-at-each-respawn behavior**, as this document's synthesis in §2.3 argues, or whether OLS's actual persistence design (once observed per item 4 above) hits some version of the same `CAP_SYS_ADMIN`/ownership check the fallback mechanism (§3.2) has to work around. This is this document's own inference, not a literally-stated fact from any research lane, and should be treated as an assumption to verify, not a confirmed conclusion.
12. **Whether a periodic `/var/lsns` reconcile sweep is actually necessary from day one**, or whether the new `TERMINATE_HOOKS` entry alone proves sufficiently reliable in practice — given the cgroup-slice precedent (two terminated test accounts' slices found still lingering) argues for building the sweep proactively, but this hasn't been tested against the namespace mechanism specifically.
